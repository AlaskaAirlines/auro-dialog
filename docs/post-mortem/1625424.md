# AB#1625424 — Regression: Page Behind an Open Non-Modal Dialog Still Scrolled

**Scope:** 8 files changed — `package.json` / `package-lock.json` (`auro-library` `^5.13.3` → `^5.14.3`), `src/componentBase.js` (deferred `disconnectedCallback` teardown and a matching `connectedCallback` rewire, see Section 3), `test/auro-dialog.test.js` (7 new tests plus 1 strengthened, run in both viewports), `docs/pages/accessibility.md` (corrected semantics, new Background Scroll section), `docs/pages/index.md` (one clarifying paragraph), `README.md` (regenerated), `docs/post-mortem/1625424.md`. The primary fix is in `auro-library` (AB#1647843); the `src/` changes keep the new lock intact across a same-document DOM move and re-establish it after a real remount. No visual or API change.

> **Branch note — do not merge as-is.** `package.json` currently pins `@aurodesignsystem/auro-library` to a local tarball (`file:../../../aurodesignsystem-auro-library-5.14.2.tgz`) so the fix can be verified before the library release is published. That path resolves only on the author's machine and is the source of the large `package-lock.json` diff. It must be replaced with `^5.14.3` and the lockfile regenerated before this merges.

## Executive Summary

A default, dismissible `auro-dialog` left the page behind it scrollable, while a `modal` dialog locked it correctly. The component had handed page scroll locking to `auro-library`'s `floatingUI` in `aeb1992`, but the library engaged the lock only when the positioning strategy resolved to `"fullscreen"` — which a non-modal dialog above the `--ds-grid-breakpoint-md` breakpoint does not. The component could not fix this locally, because the library re-evaluates and releases the lock on every reposition. The fix belongs in `auro-library` (two commits on `jjones/fix/scrollLock/AB#1647843`: `c076e79` locks for both overlay strategies, releases on `disconnect()`, and splits `disconnect({ teardown })` so a rewire no longer drops the lock; `83b2fb5` scopes the `aria-modal` removal inside `lockScroll()`'s ownership guards and makes `configure()` restore the dismissal handlers and `autoUpdate` a prior disconnect tore down). The work here is the dependency bump, one component-side guard so a same-document DOM move no longer tears the new lock down mid-flight, the regression coverage that should have existed when the behavior was delegated, and the documentation that never described the behavior at all. The same library fix resolves AB#1625435 in `auro-drawer`.

---

### Section 1 — The Problem

With a standard dialog open and page content tall enough to scroll, the page behind the dialog could still be scrolled by wheel, trackpad, touch, and the arrow and space keys. A `modal` dialog already prevented this, so the everyday and blocking presentations of the same component behaved differently.

This matters beyond tidiness. Content drifting out of view behind an open dialog is disorienting; on touch devices and with a screen reader the page can move unexpectedly while someone is reading the dialog; and the inconsistency between presentations is not something a consumer could predict from the API.

It reproduced only at desktop widths. Below the mobile breakpoint the dialog resolves to a different positioning strategy that did lock — which is why the gap survived review and manual testing.

---

### Section 2 — Root Cause (Code-Level)

The component's own scroll lock was removed in `aeb1992` ("perf: remove scroll lock as floatingUI handles lock"), which deleted `_lockPageScroll()`, `_restorePageScroll()`, `_lockTouchScroll()`, `_unlockTouchScroll()` and a breakpoint resize handler from `src/componentBase.js`, along with the `disconnectedCallback` cleanup that `e12bd72` had added.

Centralizing was correct — the lock is delicate (it has to defeat the VoiceOver three-finger swipe and track the iOS virtual keyboard) and `auro-drawer` needed the identical behavior. The error was in the premise: "floatingUI handles lock" was only true for the fullscreen strategies.

In `auro-library` `scripts/runtime/floatingUI.mjs`, `configureBibStrategy()` gated the lock on the positioning strategy:

```js
if (element.isPopoverVisible) {
  this.lockScroll(value === "fullscreen");
}
```

while `getPositioningStrategy()` returns, for `dialog` behavior:

```js
return smallerThanBreakpoint || this.element.modal
  ? "fullscreen"
  : "dialog";
```

`auro-dialog` passes `fullscreenBreakpoint: --ds-grid-breakpoint-md` via `floaterConfig` (`src/componentBase.js:180-189`). So a non-modal dialog on a viewport wider than that resolved to `"dialog"` and reached `lockScroll(false)`.

Two details made this worse than a simple missing call:

- **It actively unlocked, repeatedly.** `configureBibStrategy()` is reached from `position()`, which Floating UI's `autoUpdate` re-runs on every resize and scroll tick while the dialog is open. Any lock this component applied itself would have been released within a frame — which is why the fix had to be in the library.
- **`disconnect()` never unlocked at all.** `hideBib()` was the only unlock path, so unmounting a dialog while it was open stranded `body { position: fixed }` on the page permanently. This is the defect `e12bd72` originally fixed, lost in the same revert.

Full analysis: `auro-library/docs/post-mortem/1647843.md`.

### Section 3 — The Fix

In `auro-library` (AB#1647843, landing in 5.14.3):

1. `configureBibStrategy()` locks for the whole overlay branch — `lockScroll(true)` instead of `lockScroll(value === "fullscreen")`. Both `"fullscreen"` and `"dialog"` lay the dialog over the page with focus trapped inside it; the nested `"cover"` strategy takes the other branch and stays scrollable.
2. `disconnect()` releases the lock, and the unlock direction of `lockScroll()` no longer requires a live bib — the state teardown runs in.

In this repo: bump the dependency, add the coverage, fix the documentation, and guard the teardown path (below). The deleted `_lockPageScroll` helpers were deliberately **not** reinstated — two owners of the same body styles would fight over the saved values.

**The one component-side change: `disconnectedCallback` must not fire teardown on a DOM move.** Once the library owned the lock, `disconnect()` releasing it (fix 2 above) turned an existing latent bug into a visible one. A same-document move — `appendChild` of an already-parented node, which is how a host repositions an element — fires `disconnectedCallback` and reconnects within the same task. The old hook tore down synchronously, so a move released the page scroll lock and tore down `autoUpdate` while the dialog was still open and visible: the AB#1625424 symptom returning by a different route, with nothing left to re-lock it.

`disconnectedCallback()` now defers the teardown one microtask and bails if the element came back, with the body extracted into a private `_teardown()`:

```js
disconnectedCallback() {
  super.disconnectedCallback();
  queueMicrotask(() => {
    if (this.isConnected) { return; }
    this._teardown();
  });
}
```

A host that removes and re-inserts across separate tasks is not a move, so the teardown runs — the correct reading of that sequence. But a teardown that runs must also be undoable, and it was not: Lit does not re-run `firstUpdated()` on reconnect, and `floater.configure()` was reached only from there and from a `triggerElement` change. `_teardown()` drops the trigger listeners, runs `element.cleanup?.()`, tears down `autoUpdate` and releases the lock, so a remounted dialog came back permanently dead — no dismissal handling, a frozen position, and a page that no longer locks behind it. Cross-task remove/re-insert is not exotic: Vue `<keep-alive>`, caching tab and accordion hosts, virtualized lists, and any host that parks the node in a `DocumentFragment` in one task and inserts it in the next all do it.

So the teardown is paired with a `connectedCallback` that rewires it:

```js
connectedCallback() {
  super.connectedCallback();
  if (this.hasUpdated && this._floaterTornDown) {
    this._configureFloater();
  }
}
```

`_floaterTornDown` is set in `_teardown()` and cleared on every (re)configure. Gating on it keeps the first connect and the same-task DOM move at exactly one `configure()` call — on a move the deferred teardown never runs, so the flag is still false when `connectedCallback` fires — and it doubles as the idempotence guard on `_teardown()`, so a repeated disconnect in one task cannot invoke `floater.disconnect()` twice.

One consequence for tests: calling `el.disconnectedCallback()` by hand no longer does anything, because the element is still connected when the microtask runs. Teardown tests must remove the node for real (Section 4).

**An ARIA consequence, reviewed and accepted.** The library's `lockScroll()` sets `aria-modal="true"` on the inner `<dialog>` as part of locking, so a non-modal dialog now carries it. This is more accurate than what shipped before: `openDialog()` applies a `FocusTrap` regardless of `modal`, so content behind a non-modal dialog was already unreachable by keyboard. `docs/pages/accessibility.md` claimed the opposite ("the page behind it remains reachable") while its own Focus Management section three paragraphs later said focus is trapped. The docs were wrong, not the behavior.

### Section 4 — Test Coverage

The suite had one scroll assertion (`test/auro-dialog.test.js:253`) and it used a `modal` dialog — the one presentation that still worked. It also asserted only `document.body.style.position`, while the lock sets six properties plus the scroll offset. So the suite was green, the component was broken, and a regression that dropped `overflow: hidden`, `scrollbarGutter`, or the scroll restore would also have passed.

The suite already runs twice via `runFullTest(mobileView)` at 900×800 and 300×800, so each addition covers desktop and mobile. It goes from 41 to 48 tests per pass: seven new, one strengthened.

Three shared helpers were added: `snapshotPageScrollStyles()`, `expectPageScrollLocked()`, and `onCleanup()`. The last one matters more than it looks. These tests mutate global page state — `body { position: fixed }`, `html { overflow: hidden }`, the window scroll offset, host nodes appended to `body` — and a failed `expect()` is exactly what they exist to produce. Restoring in a trailing statement meant the first real regression left the page frozen for every test after it, in both viewport passes, so one defect arrived as a dozen unrelated failures. Restores now register with `onCleanup()` and run from `afterEach`, pass or fail.

**Tests (run in both viewports):**

1. `non-modal dialog locks page scroll on open and restores it on close (AB#1625424)` — the regression test. The desktop pass is the one that reproduced the bug.
2. `modal dialog locks page scroll on open and restores it on close` — existing test, strengthened from one property to all five locked properties, and now asserts all six are cleared on close.
3. `scroll lock restores page styles the consumer had already set` — opens with `body { overflow: scroll }` pre-set and asserts it comes back as `scroll`, not `""`. A host application may legitimately own these styles.
4. `scroll lock restores the scroll offset the page was at` — makes the page genuinely scrollable first, then asserts the *outcome* and not just the mechanism: while the dialog is open, a `window.scrollTo(0, 500)` leaves `window.scrollY` at `0`, and on close the page returns to the offset the reader left it at. The first draft asserted against `window.scrollY` at offset 0, where the lock writes `top: -0px` and the browser normalizes it to `0px` — the assertion passed while proving nothing.
5. `disconnectedCallback releases the page scroll lock while open` — covers the `disconnect()` half of the library fix. Removes the node for real and awaits a microtask, rather than calling the hook directly: with the deferred teardown, a hand-invoked `disconnectedCallback()` correctly does nothing. The pre-existing focus-trap cleanup test was converted to the same pattern for the same reason, replacing the older note about avoiding a real removal.
6. `holds the page still while the dialog repositions (AB#1647843)` — the release-on-reposition half of the library bug. It resizes the viewport for real (staying on the pass's side of the fullscreen breakpoint) and waits for `autoUpdate` to call `position()`, then asserts the page is still locked. The first draft called `floater.configureBibStrategy("dialog")` directly and asserted `floater._scrollLocked`; that picked the strategy for the library, so it skipped `getPositioningStrategy()` — the resolution that decides whether an `auro-dialog` is an overlay at all, which is the actual gap behind AB#1625424 — and it asserted a library private instead of the page. Assertions at that level belong in `auro-library`'s own scroll-lock suite.
7. `keeps an open dialog intact when it is moved in the DOM (AB#1625424)` — moves an open dialog between two hosts with `appendChild` and asserts it stays connected, stays `open`, keeps the page locked, and does *not* re-configure the floater. This is the regression test for the deferred teardown; it fails against the synchronous hook.
8. `rewires an open dialog that is remounted in a later task (AB#1625424)` — the other side of that hook. Removes an open dialog, lets the teardown run, re-inserts it, and asserts `configure()` ran exactly once on reconnect and the page is locked again. It fails without the `connectedCallback` rewire.

**Revert-proofing.** With the library fix reverted in `node_modules` (`lockScroll(value === "fullscreen")`), 7 desktop tests fail and the mobile pass stays green — exactly the asymmetry that let the bug ship, now visible in the suite. With the fix applied, all 96 pass. With the `connectedCallback` rewire disabled, test 8 fails in both passes and nothing else does.

### Section 5 — Risk Assessment

| Risk | Mitigation |
|---|---|
| Consumers relying on scrolling the page behind a non-modal dialog | Contradicted by the focus trap, which already made that content unreachable by keyboard. Documented in the Background Scroll section |
| Host application's own `body` styles being wiped | The library saves and restores prior inline values; asserted by test 3 |
| Content jump or scrollbar shift on open/close | Scroll offset is captured and restored (test 4); `scrollbar-gutter: stable` prevents the horizontal shift |
| Content inside the dialog becoming unscrollable | `.dialog-content` keeps `overflow: auto`; the library's `touchmove` blocker walks `composedPath()` and permits scrollable descendants. Verified manually |
| `modal` or mobile behavior regressing | Both remain covered, and the whole suite runs at both viewports |
| Page left frozen after a dialog unmounts while open | Library `disconnect()` now unlocks; asserted by test 5 |
| A DOM move tearing down an open dialog and releasing the lock | `disconnectedCallback` defers teardown a microtask and bails if the element reconnected; asserted by test 6 |
| Teardown deferred past a genuine unmount | The delay is one microtask, so cleanup still runs in the same task as the removal |
| A cross-task remount coming back dead, with no lock and no dismissal handling | `connectedCallback` re-runs `floater.configure()` when — and only when — a teardown actually ran; asserted by test 8 |
| The lock being reapplied moments after a real unmount | Library-side and bounded: `configureBibStrategy()` self-schedules a `setTimeout` retry when the bib has no shadow container, which `auro-dialog`'s `#bib` div never has, so a retry can re-lock the page for a few ticks after teardown (capped at 10 per floater). Observed while writing test 8; carried to AB#1647843 rather than worked around here |
| Stacked floaters — a dropdown or child dialog opened from a dialog | Untested, and called out as a risk on the ticket. See Ticket Completeness |
| `aria-modal="true"` on non-modal dialogs | Accepted deliberately; matches the existing focus trap and `auro-dropdown`'s mobile fullscreen path. Documentation corrected |
| Jumping two minor versions of `auro-library` (5.13.3 → 5.14.3) | Full suite run against the packed 5.14.x build before the bump; 82 pre-existing tests passed unchanged |

### Ticket Completeness

What AB#1625424 asks for beyond the code on this branch, and where each item stands.

**Design review — met.** The ticket's acceptance criteria include "🎨 UI/UX changes are reviewed and approved by the Design team before release." The change qualifies: while a dialog is open the background page freezes and a scrollbar gutter is reserved, so on pages whose content is taller than the viewport the gutter appears and the page stops responding to wheel, trackpad, touch and arrow keys. Design sign-off has been given for that behavior.

**`auro-drawer` (AB#1625435) — partial.** The same `auro-library` change is expected to resolve it: `getPositioningStrategy()` handles `"dialog"` and `"drawer"` on the same branch, so a non-modal desktop drawer hit the identical gate. That reasoning is cross-repo and unverified here — no drawer build was run, and no drawer regression test was added or executed against 5.14.x. AB#1625435 needs its own verification pass in `auro-drawer` before it is closed.

**Stacked and nested floaters — untested.** A dialog that opens a dropdown, or a child dialog, means two floaters holding the page at once. Each `AuroFloatingUI` instance keeps its own `_scrollLocked` and `_savedScrollStyles`, so the correct behavior — the lock stays held until the last one closes, and the page is restored to the values the *first* one saved — depends on ordering this branch never exercises. The suite here opens one dialog at a time. The ticket flags this as a risk and it remains one; it wants a test, and the natural home for it is the library's scroll-lock suite, where both owners can be constructed directly.

### Key Lessons

1. **Deleting code is not free if its tests go with it.** `aeb1992` removed a working scroll lock in favor of the library and removed the only thing that would have detected the library's gap. When delegating a behavior, keep (or add) a consumer-side test asserting the behavior still happens — the dependency, not the implementation, is what needs asserting.

2. **A test that exercises only the working configuration reads as proof and provides none.** The one scroll test used `modal`, the single presentation still covered by the library's `"fullscreen"` gate. The regression was invisible for as long as that was the only case tested. Confirm a new regression test fails with the fix reverted.

3. **Assert every property a mechanism sets, not one representative.** Checking `body.style.position` alone would have missed a regression in `overflow`, `scrollbarGutter`, `body.top`, or the scroll restore. The lock is six properties and a scroll offset; the test should be too.

4. **Make the fixture match the assertion's premise.** The scroll-offset test passed at scroll position 0 because `top: -0px` normalizes to `0px` — the assertion was true and meaningless. Any test asserting a restored value needs a non-default value to restore.

5. **Behavior that exists only in a dependency still needs documenting.** Page scroll locking appeared nowhere in `docs/`, so nothing recorded that it was expected, which presentation owned it, or where it lived. And an accessibility page can be internally contradictory for a long time without anyone noticing — the claim that the page behind a non-modal dialog "remains reachable" sat three paragraphs above the statement that focus is trapped.

6. **`disconnectedCallback` does not mean "unmounted."** It also fires on a same-document move, and the element is back before the next microtask. Any hook that releases page-level state — a scroll lock, a focus trap, an `autoUpdate` subscription — has to distinguish a move from an unmount, or repositioning the element silently dismantles it. Fixing the lock's release path is what exposed this: correcting one lifecycle bug made the adjacent one reachable.

7. **Check how often a conditional runs before trying to work around it.** The instinct on finding this bug is to re-add the lock in the component. That would have been silently undone on the next resize tick, because the library's release runs from `autoUpdate`. The library-side fix was both smaller and the only thing that actually works.

8. **Every teardown needs a matching setup.** Deferring the teardown to distinguish a move from an unmount fixed the move and left the unmount half-broken, because nothing re-ran the setup on reconnect. `connectedCallback` is the pair to `disconnectedCallback`; `firstUpdated` is not, and it never fires twice. If a hook releases state, something reachable on reconnect has to re-acquire it.

9. **A test that mutates global state must restore it in `afterEach`, not on the last line.** These tests exist to fail, and a trailing restore is the one statement a failure skips. The first draft left `body { position: fixed }` behind on failure, so a single regression surfaced as a cascade in both viewport passes and the real cause was the hardest failure to read.

10. **Assert at the level you own.** Reaching into a dependency's privates (`floater._scrollLocked`) and calling its internal entry points with hand-picked arguments proves the dependency's internals behave as transcribed, not that this component reaches them. Drive the public path, assert the observable outcome, and leave the private-state assertions in the suite that owns the private state.
